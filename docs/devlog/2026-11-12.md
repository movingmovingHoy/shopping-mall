## 공부한 것

### MyBatis 파라미터 `#{}` 규칙
- `WHERE id = #{id}`: 왼쪽 `id`는 DB 컬럼, 오른쪽 `#{id}`는 값을 넣을 자리.
- 서비스의 변수 이름(`productId`)은 상관없다. 메서드를 호출하면 **값만** 넘어간다.
  1. **단순 값 하나**: `#{}` 안의 이름 자유 (`#{abc}`도 됨)
  2. **객체 하나**: 객체의 필드 이름 (`#{name}` = `product.getName()`)
  3. **값 여러 개**: `@Param("이름")`으로 붙인 이름
- `countAll(Long categoryId)`는 `@Param`을 빼도 동작했다(직접 확인). 그래도 흔한 에러를 피하고 `findAll`과 맞추려고 남겨 뒀다.
- `useGeneratedKeys` + `keyProperty="id"`: id는 DB가 INSERT할 때 만들기 때문에 save 전에는 null이다. INSERT 후 DB가 만든 id를 객체에 넣어 준다.

### MyBatis 동적 SQL
- `<if test="categoryId != null">`: 조건이 참일 때만 안쪽 SQL을 넣는다. null이면 그 줄이 통째로 빠진다.
  - `<if>` 없이 `category_id = #{categoryId}`를 쓰면 null일 때 `= NULL` → 항상 거짓 → 빈 목록
- `<sql id>` + `<include refid>`: SQL 조각을 한 번만 쓰고 가져다 쓴다. 목록과 개수가 **반드시 같은 조건**이어야 해서 사용.
- 페이징: `LIMIT #{size} OFFSET #{offset}`, offset = `(page - 1) * size`
- **정렬 없이 LIMIT/OFFSET을 쓰면** DB가 순서를 보장하지 않아서 페이지 사이에 상품이 중복되거나 빠질 수 있다.

### MyBatis에는 변경 감지가 없다
- `product.stop()`은 메모리의 자바 객체만 바꾼다. DB에 반영하려면 UPDATE 쿼리를 **직접 호출**해야 한다.
- 그래서 패턴이 항상 **조회 → 도메인 메서드로 변경 → UPDATE**.
- 서비스 테스트에서 응답만 보지 않고 DB를 다시 조회해서 확인한다. UPDATE 호출을 빼먹으면 응답은 바뀌었는데 DB는 그대로인 상태가 된다.
- UPDATE는 필요한 컬럼만 SET한다. 수정 쿼리에 status를 넣으면, 수정 화면을 열어 둔 사이 다른 관리자가 판매중지한 상품이 다시 ON_SALE로 덮어써질 수 있다.

### 상태 변경은 setter 대신 의미 있는 메서드
- `setStatus(STOPPED)` 대신 `stop()`, setter 5개 대신 `update(...)`.
- 무엇을 바꿀 수 있는지가 메서드에 드러나고, 규칙이 생기면 그 메서드 하나만 고치면 된다.
- 도메인 단위 테스트(`ProductTest`)는 스프링/DB 없이 돌아서 가장 빠르다.

### data.sql
- `schema.sql`이 매번 DROP → CREATE 하므로 AUTO_INCREMENT도 1부터 다시 시작 → 카테고리 id가 항상 1, 2, 3이다. 그래서 테스트에서 `1L`을 고정값으로 써도 된다.
- DB에 직접 INSERT해 두면 다음 실행 때 사라진다. `data.sql`은 그걸 매번 자동으로 해 주는 것.
- 카테고리 관리 API를 만들어도 `data.sql`은 필요하다. (재시작마다 초기화, 관리자 계정은 어차피 여기서만 생김)
- 운영 단계에서는 `mode: always`를 끄고 Flyway 같은 마이그레이션 도구로 넘어간다.

- **@ModelAttribute DTO에 setter가 없으면 파라미터가 조용히 무시됨** → [troubleshooting/2026-11-12-modelattribute-setter.md](../troubleshooting/2026-11-12-modelattribute-setter.md)
