## 공부한 것

### 응답을 왜 DTO(`MemberResponse`)에 담는가
- Jackson은 객체를 JSON으로 바꿀 때 **getter가 있는 필드를 전부** 내보낸다. `Member`를 그대로 반환하면 암호화된 password까지 응답에 나간다.
- 해시라도 노출되면 안 된다. 해시를 가져가서 오프라인으로 무차별 대입을 할 수 있다.
- 비밀번호 암호화(encode)와 응답 DTO는 **별개**다. encode는 DB에 저장할 때 평문을 막는 것이고, DTO는 응답할 때 보여 줄 필드만 고르는 것이다.
- DTO를 두면 `Member`에 필드가 추가돼도 API 응답 모양은 바뀌지 않는다.

### INSERT ①: `useGeneratedKeys` (저장 후 id 받아 오기)
- `member.id`는 `AUTO_INCREMENT`라 INSERT할 때 넣지 않고 **DB가 저장하는 순간 번호를 매긴다.**
- 그대로 두면 DB만 id를 알고 자바 객체의 `id`는 null인 상태로 남는다.
- `useGeneratedKeys="true" keyProperty="id"`를 쓰면 DB가 만든 id를 객체의 `id` 필드에 채워 준다.
  ```xml
  <insert id="save" useGeneratedKeys="true" keyProperty="id">
  ```
- **언제 쓰나**: id가 AUTO_INCREMENT이고, INSERT 후에 그 id를 코드에서 써야 할 때 (응답에 id 포함, 주문 저장 후 그 id로 order_item 저장 등). UPDATE/DELETE에는 필요 없다.
- 이게 없으면 `MemberMapperTest`의 `getId()` 검증과 `MemberServiceTest`의 `findById(response.getId())`가 실패한다.

### INSERT ②: 동시 가입과 UNIQUE KEY
- 두 사람이 동시에 같은 이메일로 가입하면 **둘 다 `existsByEmail` → false**를 받을 수 있다.
  - 일반 `SELECT`는 락을 걸지 않고 스냅샷을 읽는다. 상대방이 커밋 전이면 안 보인다.
- **`@Transactional`은 락을 걸지 않는다.** 트랜잭션은 "같이 커밋하거나 같이 롤백하는 묶음"일 뿐이다. 락은 INSERT/UPDATE/DELETE나 `SELECT ... FOR UPDATE`에서 걸린다.
- 실제로 막아 주는 건 `schema.sql`의 **`UNIQUE KEY uk_member_email`**이다.
  - INSERT할 때 MySQL(InnoDB)이 UNIQUE 인덱스의 그 값에 **DB 내부 행 락**을 건다. 자바 스레드 락이 아니다.
  - 같은 값을 INSERT하는 다른 트랜잭션은 기다린다. 먼저 한 쪽이 커밋하면 Duplicate entry 에러, 롤백하면 성공한다.
  - 락은 커밋/롤백 시점에 풀린다. `@Transactional`은 락을 걸지는 않지만 **언제 풀릴지**를 정한다.
  ```
  A: existsByEmail → false     B: existsByEmail → false
  A: INSERT 성공               B: INSERT → Duplicate entry 에러
  ```
- 자바 `synchronized`로 막지 않는 이유: 서버가 여러 대면 서버마다 락이 따로라 못 막는다. DB는 하나라서 UK가 전부 막는다.
- 정리: **UK가 최종 방어선**이고, `existsByEmail`은 대부분의 경우에 친절한 409를 빨리 주기 위한 1차 체크다.

### DB 에러에는 HTTP 상태 코드가 없다
- `MySQL Error 1062` → JDBC `SQLIntegrityConstraintViolationException` → 스프링 `DuplicateKeyException`
- 아무도 안 잡으면 `ApiExceptionHandler`의 `Exception.class` 핸들러에 걸려서 **500**이 된다.
- 몇 번으로 응답할지는 우리가 정한다. 이미 있는 데이터와 충돌이므로 **409**.
- `existsByEmail`에 걸리든 UK에 걸리든 사용자 입장에서는 같은 상황이라 `code`를 `DUPLICATE_EMAIL` 하나로 통일했다. 프론트는 `code`로 분기하니까 같은 상황에 code가 두 개면 헷갈린다. "UK에서 걸렸다"는 개발자용 정보라서 응답이 아니라 **로그(`log.warn`)**에 남긴다.
- `DuplicateKeyException` 처리는 전역 핸들러가 아니라 Service에서 한다. 전역에서는 어떤 UK에 걸렸는지 몰라서 전부 "이메일 중복"으로 응답하게 된다.

### `@NoArgsConstructor` (빈 생성자)
- Jackson, MyBatis 같은 프레임워크는 **빈 객체를 먼저 만들고 필드를 하나씩 채운다.** 그래서 기본 생성자가 필요하다.
  - `MemberSignupRequest`: `@RequestBody`가 "JSON을 이 객체로 바꿔 달라"고 지시하면 Jackson이 변환한다.
  - `Member`: MyBatis가 조회 결과를 담을 때 쓴다.
- `Member`는 `access = PRIVATE`로 잠근다. MyBatis는 리플렉션으로 접근할 수 있고, 우리 코드에서는 `new Member()`를 못 써서 `create()`로만 만든다.
  - public이어도 동작은 하지만 email/role이 null인 회원을 만들 수 있게 되어 `create()`의 규칙을 우회하게 된다.
  - 생성자를 아예 안 쓰면 Java가 public 기본 생성자를 자동으로 만든다. 그래서 일부러 private으로 막는다.

### BCrypt (`PasswordEncoder`)
- 해시 = 되돌릴 수 없는 변환. 비밀번호는 되돌릴 필요가 없어서 암호화가 아니라 해시를 쓴다.
- **salt**: 매번 랜덤값을 섞어서 같은 비밀번호도 매번 다른 해시가 나온다. 레인보우 테이블 공격을 막는다.
- 결과는 60자 `$2a$10$[salt 22자][해시 31자]`. salt와 cost가 해시 안에 같이 저장된다.
- 비교는 `equals`가 아니라 `matches(평문, 해시)`. 저장된 해시에서 salt를 꺼내 입력값을 다시 해시해서 비교한다.
- 일부러 느리다(cost 10이면 약 0.1초). 무차별 대입을 어렵게 만드는 보안 장치다.

### `SELECT EXISTS (SELECT 1 ...)`
- 안쪽 쿼리는 행이 있는지만 본다(`1`은 의미 없는 값). `EXISTS`는 있으면 `1`, 없으면 `0`을 돌려준다.
- `resultType="boolean"`으로 MyBatis가 1/0을 true/false로 바꾼다.
- `COUNT(*)`는 끝까지 다 세지만 `EXISTS`는 하나 찾으면 멈춘다.

### 예외 흐름
- Service에서 `BusinessException` → `@Transactional` 롤백 → Controller는 잡지 않고 통과 → DispatcherServlet → `@RestControllerAdvice`에서 타입이 맞는 `@ExceptionHandler` 실행 → 공통 JSON 응답
- `@Valid` 실패는 컨트롤러 메서드에 **들어가기 전에** `MethodArgumentNotValidException`이 난다 → 400.
- 공통 에러(400/404/405/500)는 스프링이 던지고, 도메인 에러(`DUPLICATE_EMAIL`)는 우리가 직접 던진다.

### 테스트 종류
| 파일 | 방식 | 확인하는 것 |
|---|---|---|
| `MemberMapperTest` | `@MybatisTest` + 진짜 DB | SQL이 맞나 |
| `MemberServiceTest` | `@SpringBootTest` + 진짜 DB | 실제 흐름(중복 체크, 암호화) |
| `MemberServiceMockTest` | Mockito, DB 없음 | 진짜로 만들기 어려운 상황(UK 위반) |
| `MemberControllerTest` | `@WebMvcTest` + `@MockitoBean` | 상태 코드와 JSON 모양 |

- `@MybatisTest`는 안에 `@Transactional`이 있어서 테스트마다 롤백된다. `@AutoConfigureTestDatabase(replace = NONE)`는 H2로 바꿔치기하지 말고 MySQL `shop_test`를 쓰라는 뜻이다.
- `@Mock`은 가짜, `@InjectMocks`는 진짜(가짜 부품을 끼운 것). `@MockitoBean`은 스프링 컨테이너 안에 넣는 가짜다.
- `given(...)`은 실행 전에 대본을 쓰는 것이고, `verify(...)`는 실행 후에 호출 기록을 확인하는 것이다. void 메서드는 `willThrow(...).given(mock).method()` 형태를 쓴다.
- `@SpringBootTest`로 다 띄워도 되지만, 계층별 테스트는 **실패 원인이 좁혀지고**, 상황을 만들기 쉽고, 빠르다. 통합 테스트는 핵심 흐름만 조금 둔다.
- `jsonPath("$.code")`: `$`는 JSON 전체, `.code`는 그 안의 필드, `[0]`은 배열 첫 요소.
- Mock 테스트는 "save가 `DuplicateKeyException`을 던진다"고 **가정**한 것이다. 동시성 테스트가 아니며, 진짜 DB에서 그 예외가 나오는지는 따로 확인해야 한다.

### Git 브랜치
- 기능 하나 끝 → main에 merge → **main에서** 다음 기능 브랜치 생성. 그러면 테스트 파일은 계속 쌓여서 따로 합칠 일이 없다.

## 문제 / 해결
- 자세한 내용: [동시 가입 시 UK 위반이 409가 아니라 500으로 응답되는 문제](../troubleshooting/2026-11-10-concurrent-signup-500.md)
- **동시 가입 시 UK 위반이 500으로 응답되는 문제**: `DuplicateKeyException`이 `Exception` 핸들러에 잡혀서 500이 됐다. → Service에서 잡아 `DUPLICATE_EMAIL`(409)로 변환했다.
- **catch 범위를 너무 넓게 잡은 실수**: 처음에 `catch (Exception e)`로 써서 DB 연결 실패 같은 다른 에러도 409 "이미 존재하는 이메일"로 바뀌고 원래 에러 로그가 사라졌다. → `catch (DuplicateKeyException e)`로 좁혔다. `MemberServiceMockTest`에 "중복이 아닌 DB 오류는 그대로 던진다" 테스트를 넣어 다시 넓어지지 않게 막았다.
