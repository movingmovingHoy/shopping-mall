## 공부한 것

### 응답을 왜 DTO(`MemberResponse`)에 담는가
- Jackson은 객체를 JSON으로 바꿀 때 **getter가 있는 필드를 전부** 내보낸다. `Member`를 그대로 반환하면 암호화된 password까지 응답에 나간다.
- 비밀번호 암호화(encode)와 응답 DTO는 **별개**다. encode는 DB에 저장할 때 평문을 막는 것이고, DTO는 응답할 때 보여 줄 필드만 고르는 것이다.
- DTO를 두면 `Member`에 필드가 추가돼도 API 응답 모양은 바뀌지 않는다.

### INSERT : 동시 가입과 UNIQUE KEY
- 두 사람이 동시에 같은 이메일로 가입하면 **둘 다 `existsByEmail` → false**를 받을 수 있다.
  - 일반 `SELECT`는 락을 걸지 않고 스냅샷을 읽는다. 상대방이 커밋 전이면 안 보인다.
  - INSERT할 때 MySQL이 UNIQUE 인덱스의 그 값에 **DB 내부 행 락**을 건다. 자바 스레드 락이 아니다.
  - 같은 값을 INSERT하는 다른 트랜잭션은 기다린다. 먼저 한 쪽이 커밋하면 Duplicate entry 에러, 롤백하면 성공한다.
- 자바 `synchronized`로 막지 않는다.


### `@NoArgsConstructor` (빈 생성자)
- Jackson, MyBatis 같은 프레임워크는 **빈 객체를 먼저 만들고 필드를 하나씩 채운다.** 그래서 기본 생성자가 필요하다.
  - `MemberSignupRequest`: `@RequestBody`가 "JSON을 이 객체로 바꿔 달라"고 지시하면 Jackson이 변환한다.
  - `Member`: MyBatis가 조회 결과를 담을 때 쓴다.
- `Member`는 `access = PRIVATE`로 잠근다. MyBatis는 리플렉션으로 접근할 수 있고, 우리 코드에서는 `new Member()`를 못 써서 `create()`로만 만든다.
  - public이어도 동작은 하지만 email/role이 null인 회원을 만들 수 있게 되어 `create()`의 규칙을 우회하게 된다.
  - 생성자를 아예 안 쓰면 Java가 public 기본 생성자를 자동으로 만든다. 그래서 일부러 private으로 막는다.

### BCrypt (`PasswordEncoder`)
- 해시 = 되돌릴 수 없는 변환. 비밀번호는 되돌릴 필요가 없어서 암호화가 아니라 해시를 쓴다.
- **salt**: 매번 랜덤값을 섞어서 같은 비밀번호도 매번 다른 해시가 나온다. 레인보우 테이블 공격을 막는다.
- 결과는 60자 `$2a$10$[salt 22자][해시 31자]`. salt와 cost가 해시 안에 같이 저장된다.
- 비교는 `equals`가 아니라 `matches(평문, 해시)`. 저장된 해시에서 salt를 꺼내 입력값을 다시 해시해서 비교한다.
- 일부러 느리게 만들었다.(cost 10이면 약 0.1초). 무차별 대입을 어렵게 만드는 보안 장치다(해커의 무차별 대입 방지)

### 예외 흐름
- Service에서 `BusinessException` → `@Transactional` 롤백 → Controller는 잡지 않고 통과 → DispatcherServlet → `@RestControllerAdvice`에서 타입이 맞는 `@ExceptionHandler` 실행 → 공통 JSON 응답
- `@Valid` 실패는 컨트롤러 메서드에 **들어가기 전에** `MethodArgumentNotValidException`이 난다 → 400.
- 공통 에러(400/404/405/500)는 스프링이 던지고, 비즈니스 에러(`DUPLICATE_EMAIL`)는 직접 던진다.

### 테스트
- `@MybatisTest`는 안에 `@Transactional`이 있어서 테스트마다 롤백된다. `@AutoConfigureTestDatabase(replace = NONE)`는 H2로 바꿔치기하지 말고 MySQL `shop_test`를 쓰라는 뜻이다.
- `@Mock`은 가짜, `@InjectMocks`는 진짜(가짜 부품을 끼운 것). `@MockitoBean`은 스프링 컨테이너 안에 넣는 가짜다.
- `given(...)`은 실행 전에 대본을 쓰는 것이고, void 메서드는 `willThrow(...).given(mock).method()` 형태를 쓴다.
- `@SpringBootTest`로 다 띄워도 되지만, 계층별 테스트는 **실패 원인이 좁혀지고**, 상황을 만들기 쉽고, 빠르다. 통합 테스트는 핵심 흐름만 조금 둔다.

### 로그인 실패는 하나의 에러로
- 이메일이 없을 때와 비밀번호가 틀릴 때 둘 다 `LOGIN_FAILED`(401). 구분해서 알려 주면 가입된 이메일 목록을 알아낼 수 있다(계정 수집).
- 401 Unauthorized = "누군지 확인이 안 됐다".

### 로그인 DTO에는 형식 검사를 안 건다 (`@NotBlank`만)
- 가입 때 `@Email`을 통과한 이메일만 DB에 있다. 형식이 틀린 값은 어차피 DB에 없어서 401이 된다.
- 가입 규칙이 바뀌어도(예: 비밀번호 8자 → 10자) 로그인에 `@Size`가 없으니 기존 회원 로그인이 안 깨진다.
- DB에는 해시만 있어서 "비밀번호가 짧은 회원"을 DB 조회로 찾을 수 없다. 원래 비밀번호를 알 수 있는 순간은 로그인할 때뿐이다.

### 세션
- `getSession(true)`: 없으면 새로 만든다 / `getSession(false)`: 없으면 null. 로그아웃은 세션을 만들 필요가 없어서 `false`.
- 세션에는 `Member` 전체가 아니라 **회원 id만** 저장한다.
  - 회원 정보가 바뀌어도 세션에는 옛날 값이 남는다
  - password 해시가 세션(서버 메모리)에 들어간다
  - 세션은 사용자마다 하나씩 서버 메모리를 쓴다
- 로그인 성공 → 응답 `Set-Cookie: JSESSIONID=ABC` → 다음 요청부터 `Cookie: JSESSIONID=ABC` 자동 전송 → 서버가 그 세션에서 `loginMemberId`를 꺼낸다. 쿠키에는 열쇠(id)만 있고 정보는 서버에 있다.
- 세션 키는 `LoginSessionManager.LOGIN_MEMBER_ID` 상수 하나로 관리한다. 인터셉터와 ArgumentResolver도 같은 키를 쓴다.
- **세션 고정 공격 방지**: 공격자가 자기 세션 id를 피해자에게 심어 두고 피해자가 그 세션으로 로그인하면 공격자도 로그인 상태가 된다. 그래서 로그인할 때 기존 세션을 `invalidate()`하고 새 세션을 만든다. Postman에서 로그인을 두 번 하면 JSESSIONID 값이 바뀐다.

### 계층 분리와 실행 순서
- `MemberService.login()`은 회원 확인만 하고 세션은 모른다. HTTP 없이 테스트할 수 있고, JWT로 바꿔도 그대로 쓸 수 있다.
- 컨트롤러는 `HttpSession`을 직접 다루지 않고 `LoginSessionManager`만 호출한다.
- 예외가 나면 아래 줄은 실행되지 않는다. 그래서 로그인 실패 시 세션이 안 생긴다.
  ```java
  MemberResponse response = memberService.login(request);     // 예외 → 즉시 탈출
  loginSessionManager.login(httpRequest, response.getId());  // 실행 안 됨
  ```
- **확인 먼저, 상태 변경은 나중에.** 순서가 반대면 로그인에 실패해도 세션이 생긴다.

### 테스트 (로그인)
- **의존성 주입(DI)**: 컨트롤러는 생성자로 `MemberService`를 받을 뿐 진짜인지 가짜인지 모른다. 그래서 테스트에서 `@MockitoBean`으로 갈아 끼울 수 있다. 직접 `new`로 만들면 불가능하다.
- `@WebMvcTest`는 `@Component`를 띄우지 않아서 `LoginSessionManager`는 `@Import`로 넣었다. 빼면 스프링이 `LoginController`를 만들 때 빈이 없어서 **시작 단계에서** 실패한다(그 클래스의 테스트 전부 실패).
- `MockHttpSession`은 Mockito 가짜가 아니라 **진짜로 동작하는 세션 구현체**다. MockMvc에는 톰캣이 없어서 대신 쓴다. 상태를 준비하고(`setAttribute`) 확인하려고(`isInvalid()`) 직접 만들어 넣는다.
- `request().sessionAttribute(키, 값)` / `sessionAttributeDoesNotExist(키)`: 세션에 값이 있는지 확인한다.
- `ReflectionTestUtils.setField(member, "id", 1L)`: setter가 없는 private 필드에 **테스트에서만** 값을 넣는다.
- `verify(mock).method(...)`: 실제로 호출됐는지 확인한다. 매처(`any()`)를 하나라도 쓰면 나머지 인자도 `eq(...)` 같은 매처로 써야 한다.

## 문제 / 해결
- 자세한 내용: [동시 가입 시 UK 위반이 409가 아니라 500으로 응답되는 문제](../troubleshooting/2026-11-10-concurrent-signup-500.md)
- **동시 가입 시 UK 위반이 500으로 응답되는 문제**: `DuplicateKeyException`이 `Exception` 핸들러에 잡혀서 500이 됐다. → Service에서 잡아 `DUPLICATE_EMAIL`(409)로 변환했다.
- 자세한 내용: [로그인 응답 시간으로 가입 여부가 노출되는 문제 (타이밍 공격)](../troubleshooting/2026-11-10-login-timing-attack.md)
- **타이밍 공격**: 없는 이메일이면 BCrypt `matches()`를 건너뛰어 응답이 빨라서 시간으로 가입 여부를 알 수 있었다. → 가짜 해시로 항상 `matches()`를 실행해 시간을 맞췄다.
  - Postman에서 처음엔 10배 차이가 나 보였는데, **앱 시작 후 첫 요청이 느린 것**(클래스 로딩, JIT 등)이었다. 여러 번 번갈아 재 보니 둘 다 약 0.13~0.16초였다.
